## Déploiement SQL et comparaison locale / distante

1. Obtenir l'autorisation explicite du propriétaire pour le projet **staging** identifié. Sauvegarder ce projet et constater sa version actuelle. La comparaison ci-dessous est en lecture seule ; les migrations, comptes de test et objets Storage sont des mutations nécessitant cet accord.
2. Pour une base existante, appliquer dans l'ordre les migrations manquantes : `20260911000000_security_v2.sql` (v4), `20260914000000_notification_upsert.sql` (v5), puis **`20260914010000_admin_sessions.sql` (v6)**. Pour une nouvelle base, utiliser le schéma actuel. Ne jamais appliquer `supabase/tests/platform-contract.sql` ou `fixtures.sql` sur Supabase : ils ne servent qu'aux bases locales jetables.
3. Exécuter `select public.commerce_schema_version();` depuis le SQL Editor autorisé. Résultat final attendu : **6**. Contrôler l'index `notifications_dedupe_upsert_idx`, puis RLS et privilèges de `admin_sessions`. Construire l'index v5 peut retenir des écritures : prévoir une fenêtre adaptée au volume.
4. Déployer le nouveau code sur **toutes** les instances et retirer les anciennes instances/préviews capables de joindre la base. Une ancienne instance continuerait à accepter des cookies selon l'ancien modèle. Les anciens cookies absents du registre exigent une reconnexion unique. Sans la migration, l'accès admin échoue volontairement.
5. Exécuter **uniquement** la requête en lecture seule `supabase/tests/schema-fingerprint.sql` dans le SQL Editor staging. Exporter la cellule JSON `fingerprint` ou le résultat JSON du SQL Editor vers un fichier privé `staging-schema.json`. Aucune donnée client ni clé n'est incluse : uniquement métadonnées et empreintes de définitions.
6. Comparer à l'empreinte locale produite par le vrai PostgreSQL 17.11 :

```powershell
node scripts/compare-supabase-schema.mjs docs/security/phase2/local-schema.json staging-schema.json
```

Un écart ou un fichier malformé retourne un code non nul. Le résultat identifie les entrées manquantes, supplémentaires ou différentes. **La comparaison locale avec elle-même a seulement testé le format ; elle ne valide pas un staging.** Les quatre tests du comparateur incluent aussi RLS désactivé, RPC manquant et données malformées.

L'empreinte couvre 19 tables métier + `admin_sessions`, colonnes, contraintes, index, RLS, policies, privilèges, fonctions/RPC et `SECURITY DEFINER`/`search_path`, triggers et paramètres des deux buckets. Les définitions sont hachées pour éviter une exportation inutile de contenu. Toute différence doit être examinée : une version PostgreSQL différente ou une policy Storage supplémentaire légitime peut expliquer un écart. Le script n'applique aucune correction.

Cette égalité ne couvre pas les membres effectifs de rôles, les comptes admin, les réglages Auth, la passerelle HTTP Supabase, les ACL d'objets existants, ni les sauvegardes. Un diff vide ne remplace donc pas les tests suivants.

## Tests Supabase / authentification à exécuter en staging

- **SB01 — RLS** : créer, après accord, deux comptes confirmés A/B et leurs commandes/adresses synthétiques. Via les vraies API REST et clés anon/JWT utilisateur, A ne lit ni ne modifie B ; B ne lit ni ne modifie A ; anon ne lit aucune donnée privée. Vérifier les 19 tables métier, écritures directes refusées, catalogue public actif seulement.
- **SB02 — sessions admin** : connexion avec mot de passe et TOTP, conservation privée du cookie dans un second client de test, logout dans le premier, puis export/remboursement/stock/upload et pages dans le second → refus avant tout effet. Tester plusieurs instances, reconnexion avec rotation, expiration et un utilisateur Supabase standard face aux routes admin.
- **SB03 — disponibilité** : simuler une panne de la couche de sessions sur un staging dédié : vérification → refus ; création → pas de cookie ; logout → 503 avec message d'échec, puis nouvelle tentative après restauration. Ne pas simuler cette panne en production.
- **SB04 — RPC/grants** : anon et authenticated ne lisent ni n'écrivent `admin_sessions` et ne peuvent invoquer ses trois RPC ni les RPC commerce privilégiées. Vérifier les grants réels et les fonctions SECURITY DEFINER, `search_path=public`, absence de droit CREATE non voulu sur le schéma.
- **SB05 — rôle/MFA** : vérifier la liste effective des profils `staff/admin/founder` et les membres des rôles PostgreSQL. Les rôles Supabase privilégiés sont indépendants du cookie admin AVANA ; le TOTP AVANA ne prouve pas leur MFA Supabase. Faire inscrire et vérifier leur MFA dans les services concernés.
- **SB06 — Confirm Email / PKCE** : Confirm Email activé dans Auth → Sign In / Providers → Email ; vérifier le refus d'un utilisateur non confirmé/anonyme et d'une métadonnée utilisateur se prétendant confirmée. Deux liens magiques simultanés, chacun ouvert dans son navigateur initiateur, doivent réussir ; code rejoué ou mauvais vérificateur refusé ; destinations externes refusées. Conserver `next`/`sb_flow_id` dans les callbacks autorisés. Ne pas autoriser une origine arbitraire pour résoudre une redirection.
- **SB07 — cycle client** : login, rafraîchissement, logout et retour sur `/compte`. Vérifier cookies HttpOnly/Secure/Lax, absence de tokens dans l'URL finale, cache et logs. Une déconnexion Supabase détruit les refresh tokens concernés ; les JWT déjà émis peuvent rester valides jusqu'à expiration. Ne pas confondre cette propriété avec la révocation immédiate ajoutée au cookie admin. [Documentation Supabase](https://supabase.com/docs/guides/auth/signout).
- **SB08 — Storage** : vérifier les paramètres `avana-public`/`avana-private`, toutes les policies `storage.objects`, anciens documents déjà publics, MIME/tailles, upload non-admin refusé, SVG/contenu actif refusé, document interne inaccessible à A/B/anon, URL signée expirée refusée. Seules les images publiées prévues sont publiques ; les PDF passent par les routes contrôlées. Écrire uniquement des fichiers de test après accord.
- **SB09 — clés et abus** : clé publique du bon projet dans le navigateur ; clé service_role/secret exclusivement serveur ; aucun secret dans `.next/static`. Tester les limites via l'application et directement via Supabase Auth ; vérifier que le proxy de staging ne laisse pas falsifier les en-têtes IP de confiance.

Références : [configuration Auth](https://supabase.com/docs/guides/auth/general-configuration), [redirections](https://supabase.com/docs/guides/auth/redirect-urls). Aucun de ces tests cloud n'a été exécuté pendant cette phase.
